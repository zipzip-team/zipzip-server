# Zipzip 데이터 모델 의사결정 로그

## 1. 문서 목적

이 문서는 `docs/data-modeling/` 전체 검토에서 발견한 데이터 모델링 쟁점에 대해 가능한 대안을 비교하고, Zipzip 1차 서버 모델에 적용할 권장안을 확정한다.

이 문서의 결정은 이후 테이블별 컬럼 설계, ERD, SQL DDL, API 명세와 데이터 사전 작성의 기준으로 사용한다.

## 2. 의사결정 상태

- 상태: 채택
- 결정일: 2026-07-03
- 대상 DBMS: PostgreSQL
- 적용 범위: Zipzip 1차 공유 폴더 서버 모델
- 우선순위: 이 문서가 다른 데이터 모델링 문서의 표현과 충돌하면 이 문서의 결정을 우선한다.

## 4. 세부 의사결정

### 4.1 DM-01. 공유 폴더 행위 주체와 멤버십 무결성

#### 문제

앨범 생성자, 사진 업로더, 앨범 사진 추가자, 좋아요·댓글 작성자는 사용자이다. 그러나 단순히 `app_user_id`만 외래 키로 저장하면 해당 사용자가 대상 공유 폴더의 활성 방장 또는 멤버인지 DB 외래 키만으로는 보장할 수 없다.

#### 검토한 대안

| 대안 | 설명 | 장점 | 단점 |
|---|---|---|---|
| A. 작성자를 `app_user_id`로 저장 | 작성자 식별은 사용자를 직접 참조하고, 멤버십은 애플리케이션에서 검증한다. | 모델이 단순하고 탈퇴 후에도 작성자 식별이 안정적이다. 좋아요의 사용자 단위 중복 방지와도 잘 맞는다. | DB 외래 키만으로 공유 폴더 참여 여부를 강제할 수 없다. |
| B. 작성자를 `shared_folder_membership_id`로 저장 | 모든 공유 폴더 내부 행위가 멤버십을 직접 참조한다. | 행위 당시 참여 관계를 명시적으로 남길 수 있다. | 탈퇴·재참여 생명주기에 영향을 받고, 사용자 단위 조회와 중복 방지에 추가 조인이 필요하다. 대상 리소스와 같은 공유 폴더의 멤버십인지는 여전히 복합 제약이 필요하다. |
| C. 사용자와 멤버십을 모두 저장 | `app_user_id`와 `shared_folder_membership_id`를 함께 저장한다. | 사용자 식별과 참여 이력을 모두 직접 조회할 수 있다. | 중복 데이터의 불일치 가능성이 생기며 모든 쓰기에서 두 값을 함께 검증해야 한다. |

#### 결정

대안 A를 채택한다.

- 작성자, 생성자, 업로더, 앨범 사진 추가자는 `app_user_id`로 저장한다.
- 공유 폴더 내부 쓰기 요청은 대상 리소스가 속한 공유 폴더의 활성 `shared_folder_membership` 존재 여부를 서비스 계층에서 검증한다.
- 멤버십 행이 존재하고 상위 공유 폴더가 soft delete되지 않은 경우에만 활성 멤버십으로 인정한다.
- 방장과 멤버 모두 앨범 생성·수정, 사진 업로드, 앨범 사진 추가·제거, 좋아요, 댓글 작성을 할 수 있다.
- 앨범 삭제는 해당 앨범을 생성한 사용자만 할 수 있다.
- 사진 원본은 해당 사진을 업로드한 사용자만 수정하거나 삭제할 수 있다.
- 사진 댓글은 해당 내용을 작성한 사용자만 수정하거나 삭제할 수 있다.
- 멤버십이 종료되어도 기존 작성 데이터의 `app_user_id`는 유지한다.
- 멤버십 종료 후에는 새로운 쓰기 작업을 허용하지 않는다.

#### 판단 이유

작성자는 제품 전체에서 동일한 사용자이며, 좋아요 중복 기준도 사용자 단위로 확정되어 있다. 멤버십을 작성자 식별자로 사용하면 탈퇴와 재참여에 따라 동일 사용자의 정체성이 여러 멤버십으로 나뉜다. 따라서 작성자 식별은 사용자로 유지하고, 멤버십은 권한 판단에만 사용하는 편이 현재 요구사항에 더 적합하다.

#### 구현 규칙

- 쓰기 권한 검증과 데이터 저장은 하나의 트랜잭션 경계 안에서 처리한다.
- 앨범, 앨범 사진 포함 관계, 사진, 댓글 조회 시 상위 공유 폴더의 활성 상태도 함께 확인한다.
- DB를 직접 수정하는 운영 작업에서도 같은 멤버십 무결성 규칙을 지켜야 한다.
- 향후 DB 수준의 강제가 필요해지면 복합 외래 키 또는 트리거를 별도 의사결정으로 검토한다.

### 4.2 DM-02. 테이블별 삭제 정책

#### 문제

모든 테이블에 동일한 soft delete 정책을 적용하면 좋아요 취소, 토큰 폐기, 재참여처럼 성격이 다른 생명주기를 제대로 표현하기 어렵다. 또한 공유 폴더 삭제 시 많은 하위 행을 한 번에 갱신하면 트랜잭션 부하가 커질 수 있다.

#### 검토한 대안

| 대안 | 설명 | 장점 | 단점 |
|---|---|---|---|
| A. 모든 테이블 soft delete | 모든 삭제를 `deleted_at`으로 처리한다. | 규칙이 단순하고 복구 가능성이 높다. | 좋아요 재등록과 멤버 재참여에 partial unique가 필요하며 이벤트성 데이터가 계속 누적된다. |
| B. 모든 테이블 물리 삭제 | 삭제 요청 시 관련 행을 즉시 제거한다. | 조회 조건과 저장 공간 관리가 단순하다. | 실수 복구와 감사가 어렵고 Object Storage 삭제 실패를 안전하게 재시도하기 어렵다. |
| C. 데이터 성격별 혼합 정책 | 업무 엔티티는 soft delete, 상태성 데이터는 상태 변경, 현재 상태만 필요한 데이터는 물리 삭제한다. | 각 데이터의 실제 생명주기를 정확히 표현할 수 있다. | 테이블별 정책을 명시하고 구현해야 한다. |

#### 결정

대안 C를 채택한다.

| 테이블 | 삭제 방식 | 결정 내용 |
|---|---|---|
| `app_user` | soft delete | 사용자 탈퇴 시 `deleted_at`을 기록하고 활성 로그인을 차단한다. 동일한 Apple 계정으로 재가입하면 기존 행을 복구한다. |
| `refresh_token` | 상태 변경 후 물리 정리 | `revoked_at` 또는 `expires_at`으로 유효성을 판단하고, 보존 기간이 지난 행은 배치로 제거한다. `deleted_at`은 사용하지 않는다. |
| `shared_folder` | soft delete 후 30일 뒤 물리 삭제 | 공유 폴더 삭제의 기준점인 집계 루트로 사용한다. 사용자에게 복구 기능을 제공하지 않는다. |
| `shared_folder_membership` | 물리 삭제 | 멤버가 직접 나가거나 Zipzip 서비스를 탈퇴하면 `MEMBER` 행을 삭제한다. 재참여 시 새 멤버십 행을 생성한다. 강제 퇴장은 지원하지 않는다. |
| `device` | soft delete | 사용자가 더 이상 표시하지 않는 기기 태그를 숨긴다. |
| `shared_album` | soft delete 후 30일 뒤 물리 삭제 | 앨범 생성자만 삭제할 수 있으며 포함 관계 정리 후 행을 제거한다. |
| `shared_album_photo` | 물리 삭제 | 앨범에서만 사진을 제거하면 포함 관계 행을 삭제한다. 사진 원본과 Object Storage 객체는 유지한다. |
| `photo` | soft delete 후 30일 뒤 물리 삭제 | DB 참조와 Object Storage 객체 삭제를 분리하고 객체 삭제 성공 후 행을 제거한다. |
| `photo_like` | 물리 삭제 | 좋아요 취소 시 행을 삭제한다. 좋아요 이력은 1차 범위에서 보존하지 않는다. |
| `photo_comment` | soft delete | 댓글 삭제 시 작성 이력과 삭제 상태를 보존한다. |

#### 공유 폴더 삭제 방식

- 방장만 공유 폴더를 삭제할 수 있다.
- 삭제 요청 시 우선 `shared_folder.deleted_at`을 기록한다.
- 삭제된 공유 폴더를 사용자가 복구하는 기능은 제공하지 않는다.
- 공유 폴더가 삭제되면 그 아래 멤버십, 앨범, 앨범 사진 포함 관계, 사진, 좋아요, 댓글은 모두 접근 불가능한 것으로 판정한다.
- 모든 하위 행의 `deleted_at`을 같은 트랜잭션에서 일괄 갱신하지 않는다.
- 하위 데이터의 개별 `deleted_at`은 공유 폴더 삭제 전에 수행된 개별 삭제 상태를 보존하는 용도로 사용한다.
- 모든 조회와 쓰기는 상위 `shared_folder.deleted_at is null` 조건을 확인한다.

#### Object Storage 물리 삭제

- 사진·앨범·공유 폴더 soft delete와 동시에 Object Storage 객체를 즉시 제거하지 않는다.
- 사진의 유효 삭제 기준 시각은 PostgreSQL `least(photo.deleted_at, shared_folder.deleted_at)`로 계산한 가장 이른 non-null 시각이다.
- 물리 정리 작업은 유효 삭제 기준 시각으로부터 30일이 지난 사진을 순차적으로 조회한다.
- 객체 삭제에 성공한 사진만 DB 물리 정리 대상으로 처리한다.
- 객체 삭제에 실패하면 사진 행을 유지하여 다음 작업에서 재시도할 수 있게 한다.
- OCI Object Storage 삭제 요청은 멱등하게 처리하고 이미 없는 객체도 삭제 성공으로 간주한다.
- Object Storage 객체 삭제가 모두 성공하면 DB 부모 행을 삭제하고 정의된 FK `ON DELETE CASCADE`로 종속 행을 함께 정리한다.
- 개별 삭제한 앨범은 `shared_album` 행을 삭제하고 `shared_album_photo` 포함 관계는 FK cascade로 정리한다.
- 공유 폴더는 모든 사진 객체 삭제가 성공한 뒤 `shared_folder` 행을 삭제하고 멤버십, 앨범, 사진과 그 종속 행을 FK cascade로 정리한다.
- 30일의 유예 기간은 사용자 복구를 제공하기 위한 기간이 아니라 비동기 삭제 실패 재시도와 운영 안전성을 위한 기간이다.

#### 제약 규칙

- `photo_like`에는 `unique(photo_id, app_user_id)`를 적용한다.
- `photo_like`는 물리 삭제하므로 좋아요 취소 후 같은 사용자가 다시 좋아요를 생성할 수 있다.
- `shared_album_photo`에는 `unique(shared_album_id, photo_id)`를 적용한다.
- `shared_album_photo`는 물리 삭제하므로 앨범에서 제거한 사진을 나중에 같은 앨범에 다시 추가할 수 있다.
- 멤버십에는 `unique(shared_folder_id, app_user_id)` 일반 unique를 적용한다.
- 재참여 시 새 멤버십을 생성한다.

### 4.3 DM-03. 방장 정보의 기준

#### 문제

공유 폴더 생성자와 현재 방장을 모두 `shared_folder`와 `shared_folder_membership`에 저장하면 어느 값이 권한의 기준인지 불분명해지고 서로 다른 사용자를 가리킬 수 있다.

#### 검토한 대안

| 대안 | 설명 | 장점 | 단점 |
|---|---|---|---|
| A. `shared_folder.host_app_user_id`만 사용 | 공유 폴더가 현재 방장을 직접 참조한다. | 현재 방장 조회가 단순하다. | 방장도 참여 사용자라는 사실과 멤버십 역할이 중복된다. |
| B. 멤버십 `HOST`만 사용 | 방장과 생성자 모두 멤버십으로 해석한다. | 권한 기준이 하나로 모인다. | 최초 생성자를 영구적인 감사 정보로 구분하기 어렵다. |
| C. 생성자와 현재 역할을 분리 | 생성자는 공유 폴더에, 현재 방장은 멤버십 역할에 저장한다. | 생성 이력과 현재 권한을 명확히 분리할 수 있다. | 생성 트랜잭션에서 두 테이블의 일관성을 지켜야 한다. |

#### 결정

대안 C를 채택한다.

- `shared_folder.created_by_app_user_id`는 최초 생성자를 가리키며 변경하지 않는다.
- 현재 방장 권한은 활성 `shared_folder_membership.role = 'HOST'`를 기준으로 판단한다.
- `shared_folder`에 별도의 `host_app_user_id`는 두지 않는다.
- 공유 폴더마다 활성 방장은 정확히 한 명이어야 한다.
- 1차 범위에서는 방장 양도를 지원하지 않는다.
- 방장은 공유 폴더를 나갈 수 없으며, 나가려면 공유 폴더를 삭제해야 한다.
- 멤버만 공유 폴더에서 나갈 수 있다.
- 방장에게 멤버 강제 퇴장 권한을 부여하지 않는다.

#### 제약 규칙

```sql
create unique index uk_shared_folder_membership__host
    on shared_folder_membership (shared_folder_id)
    where role = 'HOST';
```

공유 폴더 생성 시 아래 작업을 하나의 트랜잭션에서 처리한다.

1. `shared_folder` 생성
2. 생성자의 `HOST` 멤버십 생성

DB unique index는 활성 방장이 두 명 생기는 것은 막지만 방장이 없는 상태까지 막지는 못한다. 따라서 방장 멤버십 삭제 금지와 생성 트랜잭션의 완전성은 서비스 계층에서 추가로 보장한다.

### 4.4 DM-04. 초대 코드 재사용 정책

#### 문제

초대 코드는 만료되거나 재발급되지 않는 공유 폴더의 고정 코드다. 활성 공유 폴더에만 partial unique를 적용하면 삭제된 공유 폴더의 코드가 새로운 공유 폴더에 재사용될 수 있고, 과거에 공유된 코드가 전혀 다른 공유 폴더에 연결될 수 있다.

#### 검토한 대안

| 대안 | 설명 | 장점 | 단점 |
|---|---|---|---|
| A. 활성 공유 폴더에서만 unique | 삭제 후 코드를 재사용할 수 있다. | 코드 공간을 재활용할 수 있다. | 오래된 코드가 다른 공유 폴더에 연결되는 보안·사용성 문제가 생길 수 있다. |
| B. 전체 공유 폴더에서 unique | 삭제된 공유 폴더 행을 유지하는 동안 코드를 다시 사용하지 않는다. | 구현이 단순하다. | 공유 폴더를 물리 삭제하면 과거 코드가 다시 들어오는 것을 DB가 막지 못한다. |
| C. 영구 예약 원장 | 발급 코드를 별도 원장에 기록하고 원장 행은 삭제하지 않는다. | 공유 폴더 물리 삭제 후에도 DB 제약으로 재사용을 차단한다. | 테이블 하나와 생성 트랜잭션 단계가 추가된다. |

#### 결정

대안 C를 채택한다.

- `shared_folder.invite_code`는 필수이며 생성 후 변경하지 않는다.
- 발급 전에 `invite_code_reservation.invite_code`에 코드를 삽입한다.
- `shared_folder.invite_code`는 예약 원장의 코드를 참조하며 unique로 관리한다.
- 삭제된 공유 폴더의 초대 코드는 영구적으로 재사용하지 않는다.
- 참여 요청 시 코드 일치뿐 아니라 `shared_folder.deleted_at is null`을 함께 확인한다.
- 코드는 충분한 엔트로피를 가진 무작위 값으로 생성하고 과거 코드 풀을 의도적으로 재활용하지 않는다.
- 예약 원장 삽입에서 충돌이 발생하면 서버가 새 코드를 생성해 다시 시도한다.
- 공유 폴더를 물리 삭제해도 예약 원장 행은 삭제하지 않는다.
- 초대 코드의 길이와 문자 집합은 API 보안 설계 단계에서 확정한다.

### 4.5 DM-05. 촬영일시 누락 처리

#### 문제

사진은 촬영일 기준으로 묶지만 일부 이미지에는 촬영일 EXIF가 없거나 서버가 촬영일시를 정상적으로 추출하지 못할 수 있다. `taken_at`을 필수로 두면 정상적인 이미지 파일도 업로드하지 못할 가능성이 있다.

#### 검토한 대안

| 대안 | 설명 | 장점 | 단점 |
|---|---|---|---|
| A. `taken_at` 필수 | 촬영일이 없는 업로드를 거부한다. | 모든 사진을 촬영일 기준으로 일관되게 그룹화할 수 있다. | 스크린샷, 다운로드 이미지, 메타데이터가 없는 파일의 업로드 경험이 나빠진다. |
| B. `taken_at` nullable, 미상 그룹 사용 | 촬영일이 없으면 별도 그룹으로 표시한다. | 촬영일의 의미를 왜곡하지 않는다. | 별도의 미상 그룹 UI가 필요하다. |
| C. `taken_at` nullable, `created_at` 대체 | 촬영일이 없으면 업로드 시각을 표시·정렬 기준으로 사용한다. | 업로드를 막지 않으면서 기존 날짜 그룹 UI를 유지할 수 있다. | 예외 사진은 실제 촬영일이 아닌 업로드일에 표시된다. |

#### 결정

대안 C를 채택한다.

- `photo.taken_at`은 nullable `timestamptz`로 저장한다.
- 서버는 업로드된 이미지 파일의 EXIF에서 촬영일시를 추출한다.
- 추출한 촬영일시만 `photo.taken_at`에 저장하고 EXIF 전체를 DB 컬럼으로 저장하지 않는다.
- 촬영일시를 추출한 뒤에도 이미지 파일의 EXIF를 제거하지 않고 업로드된 원본 파일을 Object Storage에 저장한다.
- 유효 표시 시각은 `coalesce(taken_at, created_at)`으로 계산한다.
- API 응답에서는 원본 `takenAt`을 nullable로 제공하여 클라이언트가 대체 여부를 알 수 있게 한다.
- 촬영일이 없는 사진을 `created_at`으로 대체했다는 사실을 DB의 `taken_at` 값으로 위장하지 않는다.

#### 판단 이유

촬영일을 알 수 없는 이미지도 공유할 수 있어야 하며, 실제 촬영일이 아닌 값을 `taken_at`에 저장하면 필드 의미가 훼손된다. nullable 원본 필드와 별도의 표시 시각 규칙을 사용하는 편이 정확성과 사용자 경험을 함께 지킬 수 있다.

### 4.6 DM-06. Refresh Token 생명주기

#### 문제

Refresh Token 해시와 폐기 시각만으로는 만료 정리, 다중 로그인, 토큰 탈취 후 재사용 탐지, 재발급 시 기존 토큰 처리 방식을 명확히 표현하기 어렵다.

#### 검토한 대안

| 대안 | 설명 | 장점 | 단점 |
|---|---|---|---|
| A. 만료될 때까지 같은 Refresh Token 사용 | Refresh Token을 반복 사용한다. | 구현이 가장 단순하다. | 탈취된 토큰의 사용 기간이 길고 재사용 공격 탐지가 어렵다. |
| B. 재발급할 때마다 Refresh Token 회전 | 한 번 사용한 토큰을 폐기하고 새로운 토큰을 발급한다. | 탈취 토큰의 재사용을 탐지하고 피해 범위를 제한할 수 있다. | 토큰 계열과 동시 요청을 안전하게 처리해야 한다. |
| C. 사용자별 Refresh Token 하나만 유지 | 새 로그인 시 기존 토큰을 모두 폐기한다. | 상태 관리가 단순하다. | 여러 기기에서 동시에 로그인하기 어렵다. |

#### 결정

대안 B를 채택하고 다중 세션을 허용한다.

- 로그인 세션마다 별도의 Refresh Token 계열을 생성한다.
- Refresh Token 사용에 성공하면 기존 토큰을 폐기하고 같은 계열의 새 토큰을 발급한다.
- 이미 폐기된 Refresh Token이 다시 제시되면 해당 토큰 계열 전체를 폐기한다.
- 로그아웃은 현재 세션의 토큰 계열을 폐기한다.
- 전체 로그아웃 기능이 필요할 경우 사용자의 모든 활성 토큰 계열을 폐기할 수 있다.
- Access Token 원문과 Refresh Token 원문은 DB에 저장하지 않는다.
- Refresh Token은 soft delete하지 않는다.

#### 필수 컬럼 방향

| 컬럼 | 역할 |
|---|---|
| `id` | Refresh Token 행 식별자 |
| `app_user_id` | 토큰 소유 사용자 |
| `token_hash` | Refresh Token 원문의 해시 |
| `token_family_id` | 같은 로그인 세션에서 회전된 토큰 계열 식별자 |
| `expires_at` | 토큰 만료 시각 |
| `revoked_at` | 토큰 폐기 시각 |
| `replaced_by_refresh_token_id` | 회전 후 발급된 다음 토큰 참조 |
| `created_at` | 발급 시각 |
| `updated_at` | 상태 변경 시각 |

#### 제약과 처리 규칙

- `token_hash`는 unique로 관리한다.
- 토큰 검증 시 서명, 만료 시각, 해시 일치, 폐기 여부를 모두 확인한다.
- 토큰 회전은 기존 토큰 폐기와 새 토큰 생성을 하나의 트랜잭션에서 처리한다.
- 만료 시간의 구체적인 길이는 애플리케이션 보안 설정으로 관리하고 DDL에 고정하지 않는다.
- 만료되거나 폐기된 토큰은 운영상 정한 보존 기간 이후 배치로 물리 삭제한다.

### 4.7 DM-07. 기기 모델의 의미

#### 문제

온보딩에서는 사용자가 주로 촬영에 사용하는 기기를 선택하지만 Zipzip이 설치된 휴대폰 정보는 별도로 입력받거나 동기화하지 않는다. 따라서 앱 설치 기기를 별도 유형으로 모델링하면 실제 제품 입력과 생명주기가 없는 개념이 추가된다.

#### 검토한 대안

| 대안 | 설명 | 장점 | 단점 |
|---|---|---|---|
| A. 기기명만 저장 | 사용자와 주 사용 촬영 기기의 표시 이름만 저장한다. | 실제 온보딩 입력과 일치하고 모델과 API가 단순하다. | 향후 다른 종류의 기기를 관리하면 모델 변경이 필요하다. |
| B. 단일 `device`에 유형 저장 | 같은 테이블에서 표시 이름과 기기 유형을 관리한다. | 향후 유형별 표시와 필터링에 활용할 수 있다. | 현재 입력받지 않는 앱 설치 기기 개념과 불필요한 필드가 생긴다. |
| C. 촬영 기기와 앱 기기를 별도 테이블로 분리 | 서로 다른 엔티티로 모델링한다. | 각 도메인을 독립적으로 확장하기 쉽다. | 현재 요구사항에 비해 테이블과 동기화 구조가 과도하다. |

#### 결정

대안 A를 채택한다.

- `device`는 물리 장비의 유일한 인스턴스가 아니라 사용자가 주로 촬영에 사용하는 기기의 표시용 태그다.
- 시리얼 번호와 UDID는 저장하지 않는다. 이미지 파일의 전체 EXIF와 위치 정보는 DB 컬럼으로 저장하지 않으며 Object Storage의 원본 이미지 파일에서는 제거하지 않는다.
- 별도 기기 유형을 저장하지 않는다.
- 한 사용자는 여러 기기 태그를 가질 수 있다.
- 활성 기기 태그는 `app_user_id`, `lower(btrim(name))` 조합으로 중복을 방지한다.
- 별도 `normalized_name` 컬럼은 원본 `name`과 불일치할 수 있으므로 두지 않는다.
- 기기 태그를 제거하면 soft delete한다.
- 로그인 전 선택한 기기는 로컬에만 저장하고, 로그인 후 공유 폴더 기능을 사용할 때 클라이언트가 서버로 명시적으로 동기화한다.
- `device`와 `photo`는 직접 연결하지 않는다.

#### 판단 이유

현재 서버가 필요로 하는 값은 온보딩에서 선택한 주 사용 촬영 기기를 공유 폴더 관리 화면에 표시하는 태그다. 앱 설치 기기는 입력받지 않으며 별도로 표시하거나 필터링하는 요구사항도 없다. 따라서 유형을 저장하지 않고 사용자와 기기명만 관리하는 것이 실제 제품 흐름과 일치한다.

### 4.8 DM-08. 채팅 뷰와 사진 댓글 관계

#### 문제

초기 모델은 공유 폴더 채팅과 사진 댓글을 별도 도메인으로 나누어 `chat_room`, `chat_message`, `photo_comment`를 모두 두었다. 그러나 변경된 제품 정의에서는 채팅이 독립 대화 공간이 아니라 공유 폴더 안의 개별 사진 댓글을 모아서 보는 화면이다.

#### 검토한 대안

| 대안 | 설명 | 장점 | 단점 |
|---|---|---|---|
| A. 별도 `chat_room`, `chat_message` 유지 | 사진 댓글과 별개로 공유 폴더 단위 메시지를 저장한다. | 독립 메시지, 읽음 상태, 실시간 채널 확장이 쉽다. | 새 요구와 달리 같은 글이 댓글과 채팅으로 이중화될 수 있고 테이블이 불필요하게 늘어난다. |
| B. `chat_message`가 `photo_id`를 참조 | 채팅 메시지를 유지하되 각 메시지를 사진에 연결한다. | 채팅 화면 전용 테이블을 유지할 수 있다. | `photo_comment`와 의미가 중복되며 댓글 수정·삭제 정책을 두 곳에서 관리해야 한다. |
| C. `photo_comment` 집계 뷰 사용 | 공유 폴더 채팅을 `photo_comment`의 공유 폴더 범위 조회로 구성한다. | 데이터 원천이 하나라 댓글과 채팅 화면이 일관되고 테이블이 단순하다. | 사진 컨텍스트가 없는 독립 메시지는 저장할 수 없다. |

#### 결정

대안 C를 채택한다.

- `chat_room`, `chat_message` 테이블은 1차 ERD에 포함하지 않는다.
- 공유 폴더 채팅 뷰는 `photo_comment`를 `photo`, `shared_folder`와 조인해 구성한다.
- 채팅 뷰의 정렬은 댓글 `created_at`, `id` 기준의 안정적인 시간순을 사용한다.
- 채팅 뷰에서 새 글을 작성하는 경우에도 특정 사진 컨텍스트를 가진 `photo_comment`로 저장한다.
- 사진 컨텍스트가 없는 독립 메시지는 1차 범위에서 저장하지 않는다.
- 채팅 뷰 조회와 댓글 작성 권한은 공유 폴더의 활성 멤버십으로 판단한다.
- 댓글 수정과 삭제는 작성자만 할 수 있다.

#### 판단 이유

제품 정의상 채팅은 사진 댓글을 모아 보는 관찰 방식이다. 별도 메시지 테이블을 유지하면 동일한 사용자 발화가 댓글과 메시지 중 어디에 저장되어야 하는지 모호해지고, 사진 상세와 채팅 화면의 동기화 규칙도 복잡해진다. 댓글을 단일 원천으로 두면 사진 상세, 공유 폴더 채팅 뷰, 삭제 정책, 권한 검증을 하나의 모델로 설명할 수 있다.

### 4.9 DM-09. 콘텐츠 수정·삭제 권한

#### 결정

| 대상 | 생성 권한 | 수정 권한 | 삭제 권한 |
|---|---|---|---|
| 공유 폴더 | 로그인한 사용자 | 방장 | 방장 |
| 앨범 정보 | 방장, 멤버 | 방장, 멤버 | 앨범 생성자 |
| 앨범 사진 포함 관계 | 방장, 멤버 | 해당 없음 | 방장, 멤버 |
| 사진 원본 | 방장, 멤버 | 사진 업로더 | 사진 업로더 |
| 사진 좋아요 | 방장, 멤버 | 해당 없음 | 좋아요를 누른 사용자 |
| 사진 댓글 | 방장, 멤버 | 댓글 작성자 | 댓글 작성자 |

- 방장 역할은 다른 사용자가 올린 사진 원본 또는 댓글을 수정·삭제할 수 있는 권한을 자동으로 포함하지 않는다.
- 앨범 이름 같은 앨범 정보 수정은 활성 방장과 멤버 모두 할 수 있지만 앨범 삭제는 생성자만 할 수 있다.
- 공유 폴더 이름 같은 공유 폴더 정보 수정과 공유 폴더 삭제는 방장만 할 수 있다.
- 사진을 앨범에서만 제거하는 요청은 `shared_album_photo` 포함 관계만 삭제하고 사진 원본은 유지한다.
- 사진 원본 삭제 요청은 `photo.deleted_at`을 기록하고 모든 앨범 포함 관계를 조회에서 제외한다.
- 수정·삭제 요청에서는 활성 멤버십 검증과 역할, 작성자, 생성자 또는 업로더 일치 검증을 작업별로 수행한다.
- soft delete 대상 콘텐츠를 다시 삭제하는 요청은 멱등하게 처리한다.
- 다른 사용자의 콘텐츠를 숨기거나 신고하는 관리 기능은 1차 범위에 포함하지 않는다.

### 4.10 DM-10. 멤버 나가기와 재참여

#### 결정

- 멤버는 본인의 공유 폴더 멤버십을 종료하고 나갈 수 있다.
- 방장 또는 다른 멤버가 특정 멤버를 강제로 퇴장시키는 기능은 제공하지 않는다.
- 멤버가 나가면 해당 `MEMBER` 멤버십 행을 물리 삭제한다.
- 나간 멤버의 기존 사진, 좋아요, 댓글은 유지한다.
- 나간 멤버는 새로운 콘텐츠를 작성하거나 기존 콘텐츠를 수정·삭제할 수 없다.
- 나간 멤버는 공유 폴더의 유효한 초대 코드를 입력하여 다시 참여할 수 있다.
- 재참여 시 새로운 `MEMBER` 멤버십 행을 생성한다.
- 재참여한 사용자는 다시 활성화된 시점부터 공유 폴더의 콘텐츠를 조회하고 새로운 콘텐츠를 작성할 수 있다.

#### 용어 주의

이 결정에서 말하는 나가기와 재참여는 Zipzip 서비스 사용자 탈퇴가 아니라 특정 공유 폴더의 멤버십 종료와 재참여를 의미한다.

### 4.11 DM-11. 사용자 탈퇴 후 재가입

#### 결정

- Zipzip 서비스 사용자가 탈퇴하면 `app_user.deleted_at`을 기록하고 모든 활성 Refresh Token을 폐기한다.
- 탈퇴 사용자가 방장인 공유 폴더는 같은 탈퇴 처리에서 soft delete한다.
- 탈퇴 사용자가 멤버로 참여 중인 공유 폴더의 `MEMBER` 멤버십은 물리 삭제한다.
- soft delete한 공유 폴더의 `HOST` 멤버십은 공유 폴더 물리 삭제 시 FK cascade로 함께 삭제한다.
- 탈퇴한 사용자의 Apple 로그인 식별자는 기존 `app_user`에 유지한다.
- 동일한 Apple 계정으로 다시 로그인하면 새로운 `app_user`를 만들지 않고 기존 행의 `deleted_at`을 해제해 복구한다.
- 복구 시 과거 공유 폴더 멤버십을 자동으로 활성화하지 않는다.
- 탈퇴 전에 나간 공유 폴더에 다시 참여하려면 해당 공유 폴더의 유효한 초대 코드를 사용해야 한다.
- 이미 삭제되었거나 초대 코드가 유효하지 않은 공유 폴더에는 다시 참여할 수 없다.

#### 판단 이유

Apple 로그인 식별자는 같은 사람을 안정적으로 식별하는 기준이다. 동일한 Apple 계정에 새 사용자 행을 만들면 과거 작성 데이터의 주체가 분리되고 unique 제약도 복잡해진다. 기존 사용자를 복구하되 공유 폴더 참여 관계는 자동 복구하지 않는 방식이 사용자 정체성과 공유 폴더 권한을 명확히 분리한다.

### 4.12 DM-12. 공유 폴더, 앨범, 사진 계층

#### 문제

하단 네비게이션의 `공유` 탭, 공유 탭 안의 공유 폴더 카드, 공유 폴더 내부의 앨범 카드, 앨범 안의 사진 목록이 서로 다른 depth를 가진다.
또한 하나의 사진이 여러 앨범에 포함될 수 있고, 사용자는 사진 삭제 시 `이 앨범에서만 제거`와 `사진 원본 삭제`를 구분해 선택한다. 이 경계를 분리하지 않으면 초대 코드, 멤버십, 채팅 뷰, 사진 원본, 앨범 포함 관계의 소속이 모호해진다.

#### 결정

- 하단 네비게이션의 공유 뷰는 `share_view`로 구분하며 DB 테이블로 만들지 않는다.
- 첫 화면의 공유 폴더 카드 하나는 `shared_folder` 한 행이다.
- 초대 코드, 방장과 멤버 역할, 멤버십, 관리, 채팅 뷰는 `shared_folder`에 속한다.
- 공유 폴더 내부의 앨범 카드 하나는 `shared_album` 한 행이다.
- `shared_folder` 하나는 여러 `shared_album`을 가질 수 있다.
- `photo`는 `shared_folder`에 속한 사진 원본이며 Object Storage 객체를 가리킨다.
- `shared_album_photo`는 `shared_album`과 `photo`의 포함 관계를 저장한다.
- `shared_album` 하나는 여러 사진을 포함할 수 있고 사진 없이도 존재할 수 있다.
- `photo` 하나는 여러 `shared_album`에 포함될 수 있다.
- `선택한 사진 공유앨범에 복사`는 새 사진 원본을 만들지 않고 `shared_album_photo` 행을 추가한다.
- `이 앨범에서만 제거`는 `shared_album_photo` 행을 삭제하고, `사진 원본 삭제`는 `photo.deleted_at`을 기록한다.
- 공유 사진 또는 공유 앨범을 로컬 저장공간으로 복사하는 플로우는 다운로드이며 서버 엔티티를 만들지 않는다.
- 로컬 저장공간 또는 로컬 앨범에서 공유 폴더로 사진을 불러오는 플로우는 사진 업로드로 처리한다.
- 별도 `album` 테이블은 두지 않는다.
- 하단 네비게이션의 앨범 뷰는 로컬 중심 기능으로 두고 서버 모델에 포함하지 않는다.
- 초대 코드 영구 예약 원장과 앨범 사진 포함 관계까지 포함한 전체 테이블 수는 11개다.

#### 최종 관계

```text
share_view(UI)
└── shared_folder
    ├── shared_folder_membership
    ├── chat_view(UI)
    ├── shared_album
    ├── photo
    │   ├── photo_like
    │   └── photo_comment
    └── shared_album_photo
```

#### 판단 이유

공유 뷰에는 여러 공유 공간 카드가 있고 각 카드에 참여 인원 수가 표시된다. 공유 폴더 상세에서는 선택한 공유 폴더 이름 아래에 여러 앨범과 공유 폴더 단위의 관리·채팅 버튼이 표시된다. 사진 원본은 공유 폴더 안에서 재사용될 수 있고 같은 사진이 여러 앨범에 들어갈 수 있으므로 사진 파일 참조는 `photo`, 앨범 포함 여부는 `shared_album_photo`로 분리한다. 채팅 뷰는 공유 폴더 안의 사진 댓글을 모아 보여주는 화면이므로 별도 테이블로 만들지 않는다.

### 4.13 DM-13. 초대 코드 영구 예약 원장

#### 결정

- `invite_code_reservation(invite_code, created_at)` 테이블을 추가한다.
- `invite_code` 자체를 PK로 사용하고 예약 행은 삭제하지 않는다.
- 예약 원장은 주요 업무 엔티티가 아니므로 UUID `id`, `updated_at`, `deleted_at`을 두지 않는다.
- 공유 폴더 생성 시 코드 예약, 공유 폴더, 방장 멤버십을 하나의 트랜잭션에서 생성한다.

#### 판단 이유

충분히 긴 무작위 코드도 충돌 확률을 낮출 뿐 영구 비재사용을 보장하지는 않는다. 삭제된 공유 폴더 행을 30일 뒤 제거하면서 비재사용 약속을 유지하려면 과거 코드의 최소 원장만 영구 보존하는 방식이 가장 단순하고 검증 가능하다.

### 4.14 DM-14. DBML과 PostgreSQL 보완 SQL의 역할

#### 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| DBML Note에만 기록 | dbdocs 화면에서 설명을 함께 볼 수 있다. | 실행 가능한 제약이 아니므로 마이그레이션에서 빠질 수 있다. |
| DBML을 포기하고 SQL만 관리 | PostgreSQL 기능을 모두 표현할 수 있다. | dbdocs ERD와 협업 가독성이 낮아진다. |
| DBML과 보완 SQL 병행 | ERD 가독성과 실행 가능한 PostgreSQL 제약을 모두 확보한다. | 두 파일의 동기화 검증이 필요하다. |

#### 결정

- `dbml/zipzip.dbml`은 테이블·컬럼·관계·일반 제약의 기준으로 사용한다.
- `dbml/postgresql-overrides.sql`은 DBML이 표현하지 못하는 partial/expression index의 기준으로 사용한다.
- 물리 마이그레이션은 두 파일의 내용을 모두 반영해야 완료된 것으로 본다.
- 보완 SQL에는 공유 폴더별 방장, 활성 기기명 unique와 사진 표시 시각 index를 정의한다. 사용자별 멤버십 unique는 DBML의 일반 unique로 정의한다.

#### 판단 이유

dbdocs용 DBML을 유지하면서 Note에만 의존하면 실제 DB와 문서가 쉽게 어긋난다. 실행 가능한 작은 보완 SQL을 함께 버전 관리하면 PostgreSQL 전용 제약을 명시적으로 테스트할 수 있다.

### 4.15 DM-15. 개별 삭제 사진·앨범의 물리 정리

#### 결정

- 사진, 앨범, 공유 폴더 삭제에 동일한 30일 운영 유예를 적용한다.
- 사진은 PostgreSQL `least(photo.deleted_at, shared_folder.deleted_at)`로 계산한 가장 이른 non-null 삭제 시각을 기준으로 정리 대상이 된다.
- Object Storage 객체 삭제가 성공한 뒤에만 사진 DB 행을 물리 삭제하고 사진 좋아요, 댓글, 앨범 포함 관계는 FK cascade로 함께 정리한다.
- 실패하면 사진 행을 남겨 재시도하며 상위 행도 먼저 삭제하지 않는다.
- 개별 삭제한 앨범은 앨범 행 삭제 시 포함 관계를 FK cascade로 정리한다. 공유 폴더는 모든 사진 객체 삭제가 성공한 뒤 공유 폴더 행을 삭제하고 전체 하위 DB 행을 FK cascade로 정리한다.
- 앨범에서만 사진을 제거하는 작업은 `shared_album_photo` 행을 즉시 물리 삭제하며 30일 정리 대상이 아니다.

#### 판단 이유

공유 폴더 전체 삭제만 정리 대상으로 삼으면 사용자가 개별 삭제한 사진과 앨범이 무기한 남는다. 같은 유예 기간과 자식 우선 삭제 순서를 사용하면 운영 규칙이 단순하고 Object Storage 실패도 안전하게 재시도할 수 있다. 다만 앨범에서만 사진을 제거하는 작업은 파일 원본을 삭제하지 않으므로 유예 없이 포함 관계만 제거한다.

### 4.16 DM-16. 공유 폴더 범위 무결성의 강제 위치

#### 결정

- 생성자·업로더·앨범 사진 추가자·작성자 FK는 `app_user`를 참조한다.
- 쓰기 트랜잭션 안에서 대상 리소스의 `shared_folder_id`, 요청 사용자의 활성 멤버십, 콘텐츠 소유자를 순서대로 검증한다.
- `shared_album_photo` 생성 시 대상 앨범과 사진이 같은 활성 공유 폴더에 속하는지 검증한다.
- 다른 공유 폴더 사용자 ID를 넣는 교차 범위 쓰기, 나간 멤버의 쓰기, 타인 콘텐츠 수정·삭제를 통합 테스트 필수 사례로 둔다.
- 운영성 직접 SQL은 서비스 규칙을 우회하므로 원칙적으로 금지하고 필요한 경우 같은 검증 절차를 적용한다.

#### 판단 이유

멤버십 FK로 행위 주체를 바꾸거나 중복 FK를 추가해도 상위 리소스와 같은 공유 폴더인지 확인하려면 복합 제약이나 트리거가 필요하다. 현재 규모에서는 사용자 정체성을 안정적으로 보존하고 서비스 트랜잭션과 테스트로 범위를 강제하는 편이 복잡도 대비 적합하다.

### 4.17 DM-17. 사진 표시 시각·정렬·시간대

#### 결정

- DB에는 `taken_at`, `created_at`을 UTC `timestamptz`로 저장한다.
- 표시 정렬 키는 `coalesce(taken_at, created_at), id`로 사용해 동일 시각에서도 순서를 안정화한다.
- 공유 폴더 사진 목록의 해당 정렬은 `idx_photo__active_display_at` partial expression index로 지원한다.
- 앨범 사진 목록은 `shared_album_photo`로 대상 사진을 좁힌 뒤 같은 표시 정렬 기준을 사용한다.
- 날짜 그룹은 클라이언트가 선택한 화면 시간대에서 계산한다. 서버가 그룹을 계산하는 API라면 요청에서 IANA timezone을 받는다.
- 별도 `taken_date` 컬럼은 두지 않는다.

#### 판단 이유

촬영일과 업로드일을 별도 원본 값으로 보존하면서 실제 화면 정렬식과 인덱스를 일치시킬 수 있다. 날짜를 UTC로 미리 고정하면 사용자의 시간대에 따라 잘못된 날짜 그룹이 생길 수 있으므로 날짜 경계는 표시 시간대에서 계산한다.

### 4.18 DM-18. 정규화·입력 길이·정리 인덱스

#### 결정

- 기기명 중복 기준은 DB의 `lower(btrim(name))` 표현식으로 계산하고 `normalized_name` 컬럼은 제거한다.
- `photo_comment.content`는 `varchar(1000)`으로 제한한다. 채팅 뷰도 `photo_comment`를 사용하므로 같은 제한을 따른다.
- Refresh Token 정리 조건이 `expires_at` 또는 `revoked_at` 각각을 사용할 수 있으므로 두 컬럼에 개별 인덱스를 둔다.
- 사용자 최초 등록 시 Apple이 이름을 제공하면 사용하고, 제공하지 않으면 클라이언트에서 표시 이름을 받아야 등록을 완료한다. 따라서 `display_name`은 `not null`을 유지한다.

#### 판단 이유

파생 정규화 값을 별도 컬럼으로 저장하면 원본과 불일치할 수 있다. 입력 길이를 명시하면 API와 DB의 계약이 분명해지고, 서로 다른 토큰 정리 조건에는 복합 인덱스 하나보다 개별 인덱스가 활용되기 쉽다.
